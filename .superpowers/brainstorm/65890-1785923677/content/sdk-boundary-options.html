SDK 在业务服务仓库中的放置方式

目标：SDK 暂时只供 go-reagent 服务使用，但边界稳定后可以整体迁移到独立仓库。

go-reagent/
├── ai/
├── agent/
├── reagent.go
├── internal/service/
└── cmd/server/

A. 继续使用根目录公共包

不新增 sdk/。服务层放入 internal/service，继续让根包承担 SDK facade。

优点

  • 改动最少
  • 符合常见 Go 仓库布局

代价

  • SDK 不是物理上的可搬迁单元
  • 仓库根身份仍偏 SDK
go-reagent/
├── sdk/  ← 可抽离岛
│  ├── ai/
│  ├── agent/
│  ├── sdk.go
│  └── internal/{workspace,tools,...}
├── internal/service/
└── cmd/reagent/

B. 单模块中的 sdk/ 可抽离岛（推荐）

服务只能依赖 sdk 的公共 API；sdk 不得依赖任何服务包。未来把 sdk/ 内容整体搬到新仓库。

优点

  • 职责和目录身份清楚
  • 当前仍保持一个 go.mod
  • 未来拆仓路径直观

代价

  • 现在需要一次 import path 迁移
  • 拆仓时还会有一次机械路径替换
go-reagent/
├── go.mod  （服务）
├── sdk/
│  ├── go.mod  （独立模块）
│  ├── ai/
│  └── agent/
└── go.work

C. sdk/ 直接做嵌套 Go Module

从现在开始模拟两个仓库，以 go.mod 强制隔离依赖。

优点

  • 边界最强
  • 未来拆仓最接近直接移动

代价

  • 测试、发布、CI 和依赖版本管理更复杂
  • SDK 尚未稳定时维护成本偏高
推荐依赖方向
cmd/reagent → internal/service → sdk → sdk/agent → sdk/ai
禁止：sdk → internal/service
